# Harness for Gemini — 에이전트 팀과 스킬 설계 팩토리

프로젝트의 도메인 특성에 맞추어 Google Antigravity / Gemini 환경에 최적화된 하네스(에이전트 팀 아키텍처, 전용 스킬, 품질 검증 체계)를 설계하고 구축한다.

---

## 핵심 원칙

1. **규격 준수**:
   - 상위 프로젝트 규칙 및 상시 컨텍스트는 `GEMINI.md`와 `AGENTS.md`에 유지한다.
   - 세부 아키텍처 및 도메인 규칙은 `.agents/rules/`에 작성한다.
   - 세부 작업 절차와 스킬은 `.agents/skills/<name>/SKILL.md`에 배치한다.
   - 에이전트에는 **"누가 일하는가(Role/Responsibility)"**를, 스킬에는 **"그 일을 어떻게 하는가(Procedure/Guidelines)"**를 명확히 분리한다.
2. **Gemini 3대 네이티브 실행 모드 매핑**:
   - 입출력이 명확하고 스크립트 실행이 가능한 작업은 **도구 기반 비동기 오케스트레이션 (모드 A)**을 적용한다.
   - 실제 브라우저 인터랙션이나 격리 검증이 필요한 경우 **서브에이전트 위임 (모드 B)**을 적용한다.
   - 복잡한 설계 조율 및 페어 프로그래밍은 **반응형 조율 (모드 C)**을 적용한다.
   - (참조: `references/gemini-execution-modes.md`)
3. **Gemini 모델 티어링 정책**:
   - 장기 계획, 시스템 아키텍처, 적대적 비판 검증에는 **Gemini Pro (Reasoning Tier)**를 배정한다.
   - 빠른 코드 구현, 린트/테스트 러너, 로그 분석, 형식 변환에는 **Gemini Flash (Execution Tier)**를 배정한다.
   - (참조: `references/model-selection-guide.md`)
4. **결정론적 품질 검증 결합**:
   - 산출물의 신뢰성을 위해 5대 품질 패턴(적대적 검증, 심사위원단, Loop-until-dry, 다각 스윕, 누락 검토자) 중 1개 이상을 필수로 연결한다.
   - (참조: `references/quality-verification-patterns.md`)
5. **점진적 공개(Progressive Disclosure)**:
   - `GEMINI.md`에는 호출 트리거와 라우팅 포인터만 간결히 유지하고, 상세 가이드는 서브문서로 관리하여 토큰 낭비를 원천 차단한다.
6. **언어 일관성**:
   - 하네스가 생성하는 산출물과 문서는 사용자가 대화에서 사용하는 기본 언어(한국어)를 준수한다.

## 단계별 구축 절차

### 0단계: 워크스페이스 현황 감사 (Audit)
1. 워크스페이스 루트의 `GEMINI.md`, `AGENTS.md`, `.agents/` 디렉토리를 점검한다.
2. 현재 상태에 따라 분기한다:
   - **신규 구축**: 하네스가 부재하거나 비어 있는 경우 1단계부터 전면 구축.
   - **기존 구성 확장**: 특정 도메인 에이전트나 스킬만 추가하는 경우 필요한 단계만 선별 실행.
   - **운영 및 유지보수**: 불일치 점검 및 동기화 수행.
3. 과거 Claude v1 유물(`TeamCreate`, `TeamDelete`, `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`)이 발견되면 Gemini 네이티브 프리미티브로 즉시 마이그레이션한다.

### 1단계: 도메인 및 제어 흐름 분석 (Domain Analysis)
1. 사용자 요구사항 및 프로젝트 도메인을 심층 분석한다 (예: GraphRAG 지식그래프 에이전트, Neo4j & Apache AGE 듀얼 백엔드).
2. 제어 흐름의 형태를 진단한다:
   - 작업 대상 목록을 사전에 결정할 수 있는가?
   - 단계 간에 엄격한 산출물 검증 및 피드백 루프가 필요한가?
   - 사용자 인터랙션(브라우저 E2E) 검증이 필요한가?
3. 프로젝트 기술 스택(HTML/Vanilla JS/CSS, Node, DB 등) 및 아키텍처를 파악한다.

### 2단계: 실행 모드 및 팀 아키텍처 설계 (Architecture Design)
1. `references/gemini-execution-modes.md`를 참고하여 실행 모드(A, B, C 또는 하이브리드)를 선택한다.
2. 6대 팀 패턴 중 가장 적합한 아키텍처를 확정한다:
   - 파이프라인, 분산·통합, 전문가 풀, 생성·검증, 감독자, 계층형 위임.
3. 품질 검증 패턴(적대적 검증, Loop-until-dry 등)의 결합 방식을 정의한다.

### 3단계: 전문 에이전트 및 역할 정의 (Agent Definition)
1. 팀을 구성할 핵심 에이전트의 페르소나, 주 임무, 입출력 포맷을 정의한다.
2. 업무 성격에 맞춰 모델 티어(Gemini Pro vs Flash)를 매핑하고 선정 이유를 기록한다.

### 4단계: 스킬 생성 (Skill Generation)
1. 에이전트들이 수행할 전문 작업 지침을 `.agents/skills/<name>/SKILL.md`로 작성한다.
2. Frontmatter(`name`, `description`)를 명확히 작성하여 필요 시에만 모델이 인지하여 로드하도록 구성한다.
3. 절차 체크리스트, 예외 처리, 산출물 템플릿을 포함한다.

### 5단계: 오케스트레이터 및 `GEMINI.md` 통합
1. 팀을 유기적으로 작동시킬 오케스트레이션 규칙을 정의한다.
2. `GEMINI.md`에 호출 키워드(트리거), 에이전트 팀 맵, 변경 이력 테이블을 갱신한다.

### 6단계: 검증 및 드라이런 (Verification)
1. 생성된 스킬의 트리거 조건(Should-trigger / Near-miss)을 점검한다.
2. Antigravity 도구(`view_file`, `run_command`, `browser_subagent`)와의 연동 정합성을 테스트한다.

### 7단계: 진화 및 피드백 루프 연계
1. 실제 프로젝트 수행 과정에서 도출된 피드백은 `harness-evolve` 스킬과 Antigravity의 `/learn` 명령어를 통해 지속적으로 하네스에 환류한다.
