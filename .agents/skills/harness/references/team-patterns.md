# 팀 구성 패턴 — 6대 기본 패턴 및 아키텍처 가이드

본 문서는 하네스 설계 시 업무의 성격에 맞춰 선택할 수 있는 6대 에이전트 팀 아키텍처 패턴을 설명한다.

---

## 1. 6대 기본 아키텍처 패턴

### 1-1. 파이프라인 (Pipeline)
- **구조**: `[요구사항/도메인 분석] → [아키텍처 설계] → [구현] → [검증/테스트]`
- **특징**: 각 단계의 출력이 다음 단계의 필수 입력이 되는 선형 의존 구조.
- **적용 분야**: 신규 기능 개발, 데이터 마이그레이션, 문서화 파이프라인.
- **주의점**: 병목이 발생하면 후속 단계가 지연되므로, 단계 간 인터페이스(입출력 스키마)를 엄격히 정의해야 한다.

### 1-2. 분산·통합 (Fan-out / Fan-in)
- **구조**:
  ```
           ┌→ [관점 A: 보안 분석]    ─┐
  [분배] ─┼→ [관점 B: 성능 최적화]  ─┼→ [종합 리포트 생성]
           └→ [관점 C: UI/접근성 검토] ─┘
  ```
- **특징**: 동일 대상에 대해 여러 독립적 관점을 병렬로 검토한 후 단일 보고서로 통합.
- **적용 분야**: 코드 리뷰, 릴리즈 감사, 종합 벤치마킹.
- **주의점**: Fan-in 단계에서 각 에이전트의 충돌하는 의견을 조율하는 가중치/합의 기준이 필요하다.

### 1-3. 전문가 풀 (Expert Pool)
- **구조**: `[요청 분석/라우터] → {인증 전문가 | 결제 전문가 | 미디어 스트리밍 전문가}`
- **특징**: 요청의 성격에 따라 가장 적합한 도메인 지식을 가진 단일 전문가에게 작업을 라우팅.
- **적용 분야**: 다양한 하위 모듈이 존재하는 대규모 웹/앱 서비스.

### 1-4. 생성·검증 (Producer-Reviewer)
- **구조**: `[생성자: 코드 작성] ⇄ [검증자: 테스트 및 보안 비판] (최대 3회 루프)`
- **특징**: 한 에이전트가 코드를 생산하고, 독립된 검증자가 엄격한 합격 기준을 통과할 때까지 피드백을 주고받음.
- **적용 분야**: 미션 크리티컬 비즈니스 로직, 금융/결제 모듈, 핵심 보안 API.
- **주의점**: 무한 루프에 빠지지 않도록 최대 반복 회수(Max Turns = 3) 및 조기 탈출 조건을 설정한다.

### 1-5. 감독자 (Supervisor)
- **구조**:
  ```
           ┌→ [작업자 1 (태스크 A)]
  [감독자] ─┼→ [작업자 2 (태스크 B)]
           └→ [작업자 3 (태스크 C)]
  ```
- **특징**: 감독자가 공유 태스크 큐와 상태를 실시간 모니터링하며, 병목이나 에러 발생 시 동적으로 작업을 재할당.
- **적용 분야**: 대규모 리팩터링, 전체 테스트 슈트 복구, 다중 서비스 배포.

### 1-6. 계층형 위임 (Hierarchical Delegation)
- **구조**: `[총괄 디렉터] → [프론트엔드 리드] → [UI 작업자], [백엔드 리드] → [API 작업자]`
- **특징**: 대규모 프로젝트를 서브 팀으로 계층 분할.
- **주의점**: 계층은 최대 2단계를 초과하지 않도록 제한하여 의사소통 오버헤드를 방지한다.

---

## 2. 에이전트 분리 및 네이밍 원칙

1. **단일 책임 원칙 (SRP)**: 한 에이전트가 "기획, 코딩, 테스트, 배포"를 전부 떠맡지 않는다.
2. **독립된 검증자 원칙**: 자신이 작성한 코드를 자신이 스스로 검증하게 하지 않고, 검증자 역할을 분리한다.
3. **스킬과 에이전트의 구분**:
   - **에이전트**: 전문 역할 정의 (Role, Persona, Focus)
   - **스킬**: 작업 수행 절차와 지침 (Step-by-step procedure, Checklist)
